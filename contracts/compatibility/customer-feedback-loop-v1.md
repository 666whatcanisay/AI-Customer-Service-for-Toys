# Customer Feedback Loop V1 compatibility

Contract version: `0.2.0`

## Change

- Adds `POST /api/v1/ai-interaction-events` with required `Idempotency-Key`.
- Adds the versioned create and receipt schemas for the three customer-service actions:
  `DIRECT_ACCEPT`, `EDITED_ACCEPT`, and `REJECTED`.
- Adds optional `interaction_id` to the existing task-local
  `POST /api/v1/ai-response-feedback` request so a submitted rejection reason
  can classify the already-saved event. Existing clients may omit it.
- Adds C-only Admin projections and human lifecycle actions under
  `/api/v1/admin/ai-feedback-loop/*`.

## Compatibility

- This is additive. Existing `0.1.0` endpoints and `feedback.schema.json` remain
  unchanged.
- B is affected as the new event producer. C is affected as the event owner and
  operations consumer. A is not affected and its badcase export/writeback
  contract is unchanged.
- Deploy C before B. A new B client must treat a missing or invalid `RECORDED`
  receipt as a failed save and must not show a local success.
- During rollback, roll back B first. C may retain already-recorded events and
  C-only workflow rows; migration downgrade is allowed only after normal backup
  and confirmation that those rows can be discarded.

## Data boundary

- The event contract carries summaries, not full conversations, customer
  profiles, orders, screenshots, or Answer Trace.
- C applies identifier replacement, whitespace normalization, and a 240
  character persistence cap. This is data minimization, not a claim of complete
  automatic redaction.
- The event timestamp and event ID are generated by C. The customer-service
  identity is the existing pilot reporter identifier; it is not authentication
  or RBAC.

## Behavior boundary

The new workflow does not generate knowledge, publish knowledge, edit Prompt,
train a model, send a customer message, change an order, or write to ERP.
Knowledge task creation and verification are explicit human operations.
