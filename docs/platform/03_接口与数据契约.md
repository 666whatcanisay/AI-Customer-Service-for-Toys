# Interfaces and data contracts

Shared contract version remains `contracts/version.json 0.1.0`. C does not modify `contracts/**`, A/B business code, shared schemas, the shared error-code registry, or API contract version in MVP-PLUS-01.

## MVP-PLUS-02 feedback-case interface supplement

`13_AI反馈接口说明.md` is the C-line implementation note for the frozen `ai-feedback.v1-draft` supplement. It adds only `GET /api/v1/admin/ai-quality/feedback-cases` and `POST /api/v1/admin/ai-quality/analysis-results` for A/C integration.

C exports only manually confirmed `ANALYZING` feedback as a minimum snapshot containing `feedback_id`, `revision`, question/answer fields, the closed five-value `feedback_type`, `content_hash`, and `created_at`. Writeback requires the matching `feedback_id + revision`, stores evidence only, and is idempotent for an identical `analysis_run_id` retry. It neither invokes an A model nor applies A suggestions.

The record starts at immutable v1 `revision=1`; C computes its `sha256:` canonical-content hash at human confirmation. Any later content amendment, additional revision, or automated action requires a separately frozen contract, shared-contract version decision, affected-line review, and rollback plan. C’s internal confirmation endpoint is not a B/A interface.

## MVP-PLUS-01 frozen experience-case interfaces

The implementation follows `docs/control/interfaces/experience-case.v1-draft.md` without changing it. These additive paths are frozen for B/C and A/C implementation; they do not promote a new shared contract version.

- `POST /api/v1/customer-experience-cases` accepts only submission fields. C forces `CUSTOMER_SERVICE_SUBMITTED`, revision `1`, and `NEW`.
- `GET /api/v1/customer-experience-cases?created_by=&review_status=` returns a status projection only: it omits review notes, reviewer identity, questions/answers, export snapshots, and A evidence.
- `GET /api/v1/admin/ai-optimization/cases/export?cursor=&size=` returns only approved snapshots and includes case/revision/export/hash evidence needed for an A evaluation.
- `POST /api/v1/admin/ai-optimization/evaluation-results` persists only matching structured evaluation evidence. It cannot trigger Prompt, knowledge, model, message, order, or ERP work.

An approved revision is immutable. C generates a single snapshot and `sha256:` content hash on approval; A writeback must match its case ID, revision, export revision, and hash. C-owned internal Admin paths for listing/detail/review and pool viewing are not a formal authorization system.

Affected lines: B consumes the new submission/status projection, and A consumes the controlled snapshot/returns evidence. No existing field or endpoint is renamed or removed. A future promotion to `contracts/**` requires a separate schema, version, changelog, compatibility review for A/B/C, and rollback plan.

## Existing C-T05 administration APIs

- `POST /api/v1/customer-suggestions` creates a suggestion with forced `SUBMITTED` status and returns retained `id` plus additive same-value `suggestion_id`.
- `GET /api/v1/customer-suggestions?reporter_id=` returns only the reporter projection; it excludes `internal_note`.
- `GET/PATCH /api/v1/admin/customer-suggestions` is lifecycle-only administration. Invalid transitions return `SUGGESTION_INVALID_STATUS_TRANSITION` with HTTP 409.
- Read-only C projections remain available at `/api/v1/admin/overview`, `/stores`, `/products`, `/products/{id}`, `/products/{id}/skus`, `/faqs`, `/safety-rules`, `/sources`, `/conflicts`, and `/import-batches`.

Source projections suppress absolute paths, raw attachment bytes, raw RTF, and raw metadata. The previous A-module availability probe remains unavailable without a separately versioned A contract and has no mock fallback.
