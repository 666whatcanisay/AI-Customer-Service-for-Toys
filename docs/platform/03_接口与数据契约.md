- Admin复用既有`GET /reply-readiness/runs/{run_id}`恢复超时运行；同一次点击始终重放同一个`Idempotency-Key`，不会自动生成重复运行。

## Reply Rule Snapshot Publication Card 3本地接口

- `POST /api/v1/admin/reply-rules/publications`：以必需`Idempotency-Key`发布指定租户/平台的完整有效快照。
- `GET /api/v1/admin/reply-rules/publication-receipts`：按租户/平台读取最小发布Receipt。
- `POST /api/v1/admin/reply-rules/{rule_id}/versions/{rule_version}/withdraw`：通过发布删除目标后的完整快照完成Receipt门控撤回。
- C内部调用A的`POST /api/admin/ai/reply-rule-publications`，沿用既有internal service identity；浏览器不持有该凭据。

发布只包含当前生效、来源仍有效、同租户/平台范围内每个rule ID的最新APPROVED/PUBLISHED版本。A Receipt必须逐项匹配publication、scope、revision、snapshot fingerprint和rule count；否则C保持上一有效发布状态。事件和Receipt不保存问题、别名、固定回复或客户正文。

候选Schema仍位于`contracts/candidates/reply-router-v1/`，共享Contract保持`0.14.0 / coordinated`且Gateway Wire保持1.0。正式跨仓版本必须等Engine消费侧接入后共同确认。

## Reply Rule Governance Card 2本地接口

`/api/v1/admin/reply-rules`提供C本地草稿、审核、不可变修订、查询和最小事件接口。它复用Bearer IAM与`knowledge.manage`，操作者由服务端Principal产生。批准必须引用当前已审核且同业务范围的Knowledge Material；事件不保存标准问题、别名或固定回复正文。

本接口尚未成为跨仓共享Contract：Gateway Wire保持1.0，`contracts/version.json`保持`0.14.0 / coordinated`。卡3已实现本仓候选快照和Receipt，但正式版本仍需等Engine消费侧接入时协调，不允许C或A单方面冻结版本。

Repository contract version remains `contracts/version.json 0.14.0 / coordinated`. Cards 2–3 keep the new schemas under the uncoordinated candidate directory and do not modify the formal shared schemas, shared error-code registry, Gateway Wire or API contract version.

## MVP-PLUS-02 feedback-case interface supplement

`13_AI反馈接口说明.md` is the C-line Provider implementation note for frozen `ai-feedback.v1`. It provides `POST/GET /api/v1/ai-response-feedback`, `GET /api/v1/admin/ai-quality/badcases`, and `POST /api/v1/admin/ai-quality/analysis-results`.

C accepts B submissions only with a scoped `Idempotency-Key`, forces `NEW`, and returns B's minimum personal history projection. C exports only manually confirmed `ANALYZING` feedback through `/badcases`; it includes the immutable `feedback_id`, `revision`, `content_hash`, and closed five-value `feedback_type`. A writeback must match feedback ID, revision, hash, and type; it stores evidence only and is idempotent for an identical `analysis_run_id` retry. It neither invokes an A model nor applies A suggestions.

The record starts at immutable v1 `revision=1`; C computes its `sha256:` canonical-content hash at human confirmation. `/feedback-cases` is not provided and must not be consumed. Any later content amendment, additional revision, or automated action requires a separately frozen contract, shared-contract version decision, affected-line review, and rollback plan. C’s internal confirmation endpoint is not a B/A interface.

## MVP-PLUS-01 frozen experience-case interfaces

The implementation follows `docs/control/interfaces/experience-case.v1-draft.md` without changing it. These additive paths are frozen for B/C and A/C implementation; they do not promote a new shared contract version.

- `POST /api/v1/customer-experience-cases` accepts only submission fields. C forces `CUSTOMER_SERVICE_SUBMITTED`, revision `1`, and `NEW`.
- `GET /api/v1/customer-experience-cases?created_by=&review_status=` returns a status projection only: it omits review notes, reviewer identity, questions/answers, export snapshots, and A evidence.
- `GET /api/v1/admin/ai-optimization/cases/export?cursor=&size=` returns only approved snapshots and includes case/revision/export/hash evidence needed for an A evaluation.
- `POST /api/v1/admin/ai-optimization/evaluation-results` persists only matching structured evaluation evidence. It cannot trigger Prompt, knowledge, model, message, order, or ERP work.

An approved revision is immutable. C generates a single snapshot and `sha256:` content hash on approval; A writeback must match its case ID, revision, export revision, and hash. C-owned internal Admin paths for listing/detail/review and pool viewing are not a formal authorization system.

Affected lines: B consumes the new submission/status projection, and A consumes the controlled snapshot/returns evidence. No existing field or endpoint is renamed or removed. A future promotion to `contracts/**` requires a separate schema, version, changelog, compatibility review for A/B/C, and rollback plan.

## Existing C-T05 administration APIs

- `POST /api/v1/customer-suggestions` creates a suggestion with forced `SUBMITTED` status and returns retained `id` plus additive same-value `suggestion_id`.
- `GET /api/v1/customer-suggestions?reporter_id=` returns only the reporter projection; it excludes `internal_note`.
- `GET/PATCH /api/v1/admin/customer-suggestions` is lifecycle-only administration. Invalid transitions return `SUGGESTION_INVALID_STATUS_TRANSITION` with HTTP 409.
- Read-only C projections remain available at `/api/v1/admin/overview`, `/stores`, `/products`, `/products/{id}`, `/products/{id}/skus`, `/faqs`, `/safety-rules`, `/sources`, `/conflicts`, and `/import-batches`.

Source projections suppress absolute paths, raw attachment bytes, raw RTF, and raw metadata. The previous A-module availability probe remains unavailable without a separately versioned A contract and has no mock fallback.
