# customer-efficiency.v1 C Provider

## Scope and compatibility

This is the C-owned consumable Provider note for `customer-efficiency.v1`. It implements only aggregate customer-efficiency metrics. `contracts/**` remains `0.1.0` and is not modified by this task.

The provider stores neither customer-service text, customer identifiers, employee identifiers, store/product/order data, nor ranking/performance fields. It is an operational trial/test metric surface, not a personnel-performance report.

## B to C event write

`POST /api/v1/customer-efficiency-events`

Required request header: `Idempotency-Key` (non-blank, at most 255 characters).

```json
{
  "event_type": "AI_REQUEST",
  "occurred_at": "2026-07-27T09:00:00Z"
}
```

`event_type` is exactly one of:

- `AI_REQUEST`
- `DIRECT_ADOPTION`
- `EDITED_ADOPTION`
- `NOT_ADOPTED`

`occurred_at` is optional. When supplied, it must contain a timezone offset; when absent, C supplies the current UTC time. Unknown fields are rejected, so raw question/answer/customer/employee content cannot enter this event API.

The first accepted request returns `201`:

```json
{
  "event_id": "CEE-20260727-ABCDEF123456",
  "event_type": "AI_REQUEST",
  "occurred_at": "2026-07-27T09:00:00Z",
  "created_at": "2026-07-27T09:00:01Z"
}
```

The same `Idempotency-Key` with an identical canonical payload returns `200` and the original result. The same key with a different payload returns `409 CUSTOMER_EFFICIENCY_IDEMPOTENCY_CONFLICT`. C stores the key and canonical request fingerprint only for replay safety; it does not store the request body beyond the declared event fields.

## C to A aggregate summary

`GET /api/v1/admin/ai-quality/customer-efficiency/summary?window_start={optional}&window_end={optional}`

This is the A-consumable aggregate summary endpoint. It returns no event rows or raw customer-service content.

```json
{
  "summary_version": "customer-efficiency.v1",
  "generated_at": "2026-07-27T10:00:00Z",
  "window_start": "2026-07-27T00:00:00Z",
  "window_end": "2026-07-27T10:00:00Z",
  "ai_request_count": 8,
  "direct_adoption_count": 2,
  "edited_adoption_count": 2,
  "not_adopted_count": 3,
  "adoption_rate": 0.5
}
```

The C Admin dashboard reads the same aggregate definition from `GET /api/v1/admin/customer-efficiency/summary`.

## Metric definitions and statistic window

| Metric | Definition |
| --- | --- |
| `ai_request_count` | Count of `AI_REQUEST` events in the window. |
| `direct_adoption_count` | Count of `DIRECT_ADOPTION` events in the window. |
| `edited_adoption_count` | Count of `EDITED_ADOPTION` events in the window. |
| `not_adopted_count` | Count of `NOT_ADOPTED` events in the window. |
| `adoption_rate` | `(direct_adoption_count + edited_adoption_count) / ai_request_count`; `0.0` when `ai_request_count` is zero. |

Windows are `[window_start, window_end)`: the start is included and the end is excluded. Both supplied bounds must include a timezone and `window_end` must be later than `window_start`; otherwise C returns `422 CUSTOMER_EFFICIENCY_INVALID_WINDOW`. When bounds are omitted, C uses the current UTC-day start through the `generated_at` instant.

`summary_version` is the literal `customer-efficiency.v1`; `generated_at` is C's UTC summary-generation time. Counts are aggregate event counts, not a claim that each event type belongs to a one-to-one conversation, customer, or employee record.

## C Admin dashboard boundary

`/customer-efficiency` shows only the five system metrics, version, generated time, window, and formula. It deliberately has no employee list, ranking, score, performance assessment, event detail, Prompt action, knowledge publication, customer action, order change, or ERP action.

The `/admin/` namespace is only the current test-portal boundary. Formal authentication, authorization, sensitive-view audit records, retention, and production-security certification are not implemented or claimed.
