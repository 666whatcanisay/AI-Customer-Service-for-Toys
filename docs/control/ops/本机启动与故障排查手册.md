## 笔记本通过公司 Wi-Fi 访问

此模式仍然只适用于隔离的测试数据和“仅供建议、禁止自动发送”的演示，不能作为生产部署。两台电脑不需要、也不应复制整个前端；前端、A、C、Ollama 和测试数据都运行在主电脑，笔记本只用浏览器访问页面。

1. 让主电脑和笔记本连接到同一个公司 Wi-Fi 或同一个受控局域网。`127.0.0.1` 只代表“当前这台电脑”，笔记本访问 `127.0.0.1:5173` 只会访问笔记本自己，不能访问主电脑。
2. 将 `scripts\windows\config.local.ps1.example` 复制为本机的 `config.local.ps1`（如尚未创建），保留 `LanBindAddress = '0.0.0.0'` 和 `AllowPublicNetwork = $false`。新入口会显式启用 LAN 模式，原来的“启动AI客服.bat”仍保持本机模式。
3. 默认把 `LanAdvertisedHost = ''` 留空。脚本会从已连接的物理网卡中选择唯一的私有 IPv4，自动排除 `127.0.0.1`、`169.254.*`、断开网卡、虚拟网卡、WSL 和 Docker；若有多个候选地址，脚本会停止且列出候选值，必须在 `LanAdvertisedHost` 中明确填入主电脑的地址，例如 `192.168.1.20`。公有 IP、虚拟网卡 IP 和不存在的本机 IP 会被拒绝。
4. 在主电脑双击 `scripts\windows\启动局域网客服.bat`。它会让 A/C/B 分别监听 `0.0.0.0:8000`、`0.0.0.0:8011`、`0.0.0.0:5173`，并为前端设置 `VITE_RAG_API_BASE_URL=http://主电脑IP:8000` 与 `VITE_PLATFORM_API_BASE_URL=http://主电脑IP:8011`。A 和 C 均收到显式的 `CORS_ALLOWED_ORIGINS`，仅包含局域网页面、本机 `127.0.0.1` 和 `localhost` 三个来源，绝不使用通配符。
5. 启动完成后，主电脑可继续使用 `http://127.0.0.1:5173/`；笔记本在浏览器打开脚本显示的局域网页面，例如 `http://192.168.1.20:5173/`。可双击 `检查局域网客服状态.bat` 查看两个地址、三个监听地址、Ollama/模型、迁移、测试包、47 条知识同步、`model_configured`、网络类型、防火墙提示与日志目录。

Windows 将当前 Wi-Fi 标记为 `Public` 时，局域网启动默认会阻止并说明原因；请在 Windows“设置 → 网络和 Internet → Wi-Fi → 当前网络”的网络配置文件中改为 `Private` 后再启动。`AllowPublicNetwork = $true` 是显式风险覆盖，会在启动时给出警告；它不会关闭防火墙，也不会创建放通整个网络的规则。

公司 Wi-Fi 可能启用“客户端隔离/AP isolation”。主电脑已正常启动但笔记本打不开页面时，可在笔记本运行 `Test-NetConnection 192.168.1.20 -Port 5173`，并对照主电脑的 LAN 状态脚本：若主电脑本机页面正常、同网段地址无法到达且防火墙规则已由管理员按 Private 网络正确配置，很可能是设备隔离。可先让两台电脑连接同一手机热点复测；热点可通而公司 Wi-Fi 不通，即应联系网络管理员处理隔离策略，而不是复制前端到笔记本或关闭主电脑防火墙。

该原始包所有条目位于单一顶层目录，而 C 只接受根目录 manifest.json。启动器会仅在 RuntimeDirectory\test-packages 中生成临时标准化副本：它不解压到桌面、不改写原 ZIP、不提交副本，也会先请求 C 的预检接口。若 ZIP 无法安全识别为单一顶层目录，启动会失败而不会导入。

预检和导入只接受测试包：tenant_id 必须为 TENANT-PDD-SM-TEST，test_data_mode=true，production_usable=false，allow_auto_send=false。成功导入后应有 1 个店铺、5 个商品、18 个 SKU/组合、28 条评测和 47 条 RAG export。

## 一键启动流程

双击 scripts\windows\启动AI客服.bat。启动器严格按下列顺序执行：

1. 验证本地配置、Python、Node、pnpm、Ollama 地址和 qwen3.5:9b。
2. 检查 C、A、B 端口；未知端口所有者会阻断启动，绝不按端口强杀。
3. 设置 DATABASE_URL，并在 platform_backend 中执行 PlatformPythonPath -m alembic upgrade head。迁移失败时 C 不会启动。
4. 启动 C 并等待 /health。
5. 查询测试包；已存在 TestKnowledgePackageId 时跳过重复导入，否则按配置预检和导入 ZIP。
6. 启动 A 前显式设置：

       LLM_PROVIDER=ollama
       LLM_MODEL=OllamaModel
       LLM_BASE_URL=OllamaBaseUrl
       PLATFORM_API_BASE_URL=http://127.0.0.1:8011

7. 启动 A，等待 /api/health，并持续检查 /api/status。只有 ready=true、model_configured=true、initialization_error=null 才继续。
8. AutoSyncTestKnowledge=true 时调用 POST /api/test-knowledge/sync/PDD-SM-2026-001-TEST，要求 synced_items=47 且 collection_count=47。
9. 从 C 已导入的店铺、商品和 SKU 生成一次 A /api/chat smoke。答案必须有来源，且不得为“大模型尚未配置”或“大模型请求失败”。
10. 启动 B，并等待页面 HTTP 200。

成功后服务保持运行，直到用户执行停止脚本。

## 状态与停止

双击 scripts\windows\检查AI客服状态.bat。状态脚本显示：

- Ollama 地址、健康状态和模型。
- C、A、B 的受管 PID、端口和 health。
- C 的 alembic revision。
- 配置的测试包是否存在。
- 最近一次 A 同步的 package_id、synced_items 和 collection_count。
- A 的 ready、model_configured 和 initialization_error。
- 页面地址、日志目录和局域网模式。

端口监听状态会优先显示 PID；如果系统不允许读取监听 PID，但 health 已成功，显示为“health 已确认”。这不是未知进程的放行：启动前的未知端口检查仍会阻断启动。

只使用 scripts\windows\停止AI客服.bat 停止。它按 B、A、C 的顺序处理，且只终止运行记录中 PID、可执行路径和启动时间一致的进程。系统未公开命令行时，同一可执行路径与启动时间仍作为身份校验；任何不一致都会拒绝停止并要求人工核对。

## 常见故障

| 现象 | 处理 |
| --- | --- |
| C health 正常但业务接口报数据库错误 | 检查 PlatformDatabaseUrl；启动器会自动执行迁移，也可在 platform_backend 中手动运行 python -m alembic upgrade head。 |
| 启动在 C 前失败 | 查看迁移错误。修正 SQLite 路径或数据库权限后重试；脚本不会启动 C。 |
| Ollama 不可用或模型缺失 | 启动 Ollama，并确认配置地址的 /api/tags 含 qwen3.5:9b；脚本不会下载模型。 |
| A 未就绪或 model_configured=false | 检查 A 日志；确认 Ollama 地址可用。不要启动 B 或将检索兜底视为真实模型回答。 |
| 测试包不存在 | 设置 TestDataPackagePath 和 AutoImportTestData=$true；确认 ZIP 是获准的测试包。 |
| 测试包已存在 | 这是正常幂等行为；脚本跳过导入并继续同步。 |
| 47 条校验失败 | 查看 C 导入、A 同步和 A 日志；不要继续把页面当作完整演示。 |
| 端口被未知进程占用 | 人工检查 PID、可执行路径、命令和工作目录；不要用任务管理器按端口盲目结束。 |
